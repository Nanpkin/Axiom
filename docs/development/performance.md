# 性能预算与验收

**V1 provisional targets：以下均为初始工程目标，尚未实测，不是承诺。发布前必须按代表性硬件实测校准，并保留修改原因与前后证据。** CPU-first；内存是次级约束，但不得泄漏或无界增长。所有指标必须与正确性测试一起通过。

0001 已产出 Engine-only 短基线（本机历史记录），有实际微基准、有限速输入、风暴和 idle 读数；它不包含真实规则/宿主/Provider，不替代本文的完整产品预算与验收。

## 开发期政策（2026-09-27 用户明确调整）

CPU 始终是设计输入；开发期优先选择适用且低开销的状态检测方式和处理策略，不要求每轮、每个 Provider 或每次性能相关改动都运行基准。用户电脑在 AI 开发时同时处理其他工作，不应要求其为常规开发腾出空闲环境，也不把混合负载下的读数作为严谨验收依据。

1. **常规开发**：审查通知源及订阅范围、按需启停、空闲等待、去重/合并、受影响规则索引、必要期限调度和有界队列/重试。按改动保留有意义的行为测试；这些证明策略与正确性，不证明数值达标。没有异常或待比较方案时，无需仅为完成计划运行 ETW、游戏测试或长时间基准。
2. **针对性诊断**：发现持续 CPU、忙循环、通知风暴、异常重试、泄漏，或多个检测方案的成本无法合理判断时，使用能解决该疑问的最小测量/计数/追踪。混合负载可帮助定位问题，但须标注干扰和局限，不据噪声调整阈值、宣布回归或反复优化微小差异。可复现的异常不能以“暂缓性能测量”为由忽略。
3. **阶段性与发布验证**：有实际可执行的后台场景后，在环境和任务安排合适时测代表性开销；V1 发布前按本文完成产品范围内的验证与目标校准。以下耗时、重复次数、游戏和硬件矩阵是正式验收规范，不是日常开发清单。
4. **必要轮询例外**：仍须在 ADR 说明通知 API 不适用证据、容忍延迟、间隔、按需启停/退出条件与成本预期，并记录后续测量场景和时点；开发期不要求先获得准确 CPU 数字才能实施已明确的例外。发布前验证实际成本，不放宽禁止无理由轮询的原则。

计划可将数值测量明确安排到阶段验证，不把“暂未测量”作为普通功能交付的默认阻塞；不得把这种安排写成测试已通过或性能已达标。正确性、权限、误执行防护与资源释放仍按对应 contract 验证。

## 计量口径

测量 Axiom Service + 所有活动 Session Agent + 其他已启用后台子进程的总和；UI 关闭，远程/Web 关闭。早期只有 Engine harness 时单列“Engine-only”，禁止宣称完整后台达标。测试期间记录 CPU/OS/.NET/电源模式、版本提交、构建配置、规则和 Provider 数、模式与例外、工具开销。

主要指标 `CPU ms/s = Σ进程 CPU 时间毫秒 / 墙钟秒数`。单核等价 CPU% = CPU ms/s ÷ 10；任务管理器式整机百分比另除以逻辑处理器数 N。报告两者和 N，不能靠多核归一化稀释开销。“接近 0”绝不只看任务管理器四舍五入为 0%。

应用主动唤醒指 Axiom 调度器/轮询/flush/诊断主动到期触发，分别归因；OS 外部通知和 .NET 运行时活动另统计。ETW context switches 不等同于应用主动唤醒，不能互换。报告均值、按 1 秒窗口的 p95/p99、总 CPU、唤醒来源、分配/GC、I/O 和峰值队列。

## V1 provisional targets

参考场景先采用一台 Windows 11 x64、至少 8 逻辑处理器、16 GB RAM、SSD 的机器，记录确切型号；发布前再覆盖一台较弱 CPU 与游戏主机。Release、无调试器，预热 2 分钟，每组至少 10 分钟、重复 3 次；游戏每次至少 15 分钟。

| 场景/指标 | 正常模式初始目标 | 轻量模式初始目标 |
|---|---|---|
| 静稳 idle：100 条规则、5 个激活 Capability、状态稳定，无 pending deadline | 总 CPU 均值 ≤ 1 ms/s（单核 0.1%），p95 1 秒窗口 ≤ 10 ms/s | 总 CPU 均值 ≤ 0.5 ms/s（单核 0.05%），p95 ≤ 5 ms/s |
| 空配置、空日志缓冲、无 deadline 的应用主动周期唤醒 | 0；不得有固定 tick/heartbeat | 0；不得有采样/flush 空转 |
| 稳定规则场景的可避免维护唤醒 | 目标 ≤ 1 次/分钟，逐个归因；不是允许引入定时器的配额 | 目标 0；必要正确性 deadline 单列且不可漏触发 |
| sparse rule dispatch：1,000 条规则中事件只依赖 10 条 | 候选评估数 ≤ 10，不随无关规则线性增长 | 相同保留依赖保证 |
| 无 debounce 的 Engine-only 单事件到 Intent 延迟，100 事件/秒 | p95 ≤ 5 ms，p99 ≤ 20 ms | 对保留规则相同；不包含 OS/硬件设置时延 |
| 非必要观察器退出/模式切换后的释放 | 无剩余订阅/计时器泄漏 | 2 秒内释放可取消资源；在途例外单列且不假报完成 |
| 混合负载且至少一个可暂停昂贵观察器 | 记录基线 | 相比正常降低 CPU 或主动唤醒 ≥ 30%；另一项不显著恶化，保留规则结果一致 |
| 没有可削减依赖 | 满足 idle 预算 | 可无下降，不强求 30%；声明全部工作必要，不退化正确性 |
| 后台内存（Service + 1 Agent，UI 关） | Private Bytes 先以 ≤ 200 MiB 为观察目标 | 不要求为降低内存而额外 GC；不持续增长 |

参数是拟定测试夹具，不代表已实现 5 个 Provider。实际 V1 Provider 数量变化后报告两个结果：固定可比较夹具与真实启用配置。轻量模式若有用户保留的高成本例外导致超预算，必须列出并优化/校准目标，不能隐藏到“必要”分类后声称无条件达标。

## 游戏负载验收

同机、同电源/驱动/游戏设置、相同可复现片段，交错执行 Axiom 关闭 / 正常 / 轻量，多次对照；记录后台竞争、温度和测量噪声。暂定平均 FPS 下降 ≤ 1%、p99 帧时间恶化 ≤ 2%；差异若接近或低于重复测量噪声，标为未检出/不确定，不伪造收益。出现相关 stutter 即使平均值通过也要分析。

静稳游戏场景不允许出现来源不明的周期后台唤醒；有真实进程/会话/用户时间事件时，记录必要工作和延迟，不用禁用核心规则换成绩。对正常/轻量分别测系统 CPU trace、Axiom 唤醒与线程调度、游戏帧时间；游戏测量只能在真实宿主/Provider 可用后完成。

## 工具与步骤

1. BenchmarkDotNet：隔离测 StateStore 更新、索引查找、规则评估、分配；固定参数矩阵并输出环境信息。它不能证明整个产品后台零唤醒。
2. ETW / WPR + Windows Performance Analyzer：分析进程/线程 CPU、定时唤醒、调度、I/O；按需短时 trace，并比较采集开销。PerfView 可辅助 .NET 分配/GC/CPU 分析。
3. harness 用 fake clock/provider 生成可重放输入；覆盖无工作 idle、100/1,000/10,000 规则、100 与 1,000 事件/秒、有界事件风暴、失败退避、模式切换和 UI 退出。
4. 确定性测试断言无任务时无逻辑计时器；系统 trace 验证真实实现无忙等待。微基准不使用共享 CI 的噪声阈值作唯一发布门槛。
5. 将原始产物保存于未纳入 Git 的 `artifacts/performance/<run-id>`，提交小型结果摘要（环境、命令、提交、表格、证据位置、限制）。不得提交含敏感系统信息的原始 trace。

官方工具说明：[ETW](https://learn.microsoft.com/en-us/windows/win32/etw/about-event-tracing)、[WPR/WPA](https://learn.microsoft.com/en-us/troubleshoot/windows-server/support-tools/support-tools-xperf-wpa-wpr)、[BenchmarkDotNet](https://benchmarkdotnet.org/)。工具选择不代表已安装或已执行。

## 门槛与校准

第一阶段已记录 Engine-only 基线。之后每加入 Provider 都审查检测方式、激活范围和工作策略；增量数值测量按上方开发期政策安排，不要求随每次接入执行。发布前完成全进程、空闲、游戏、切换、长时间稳定性矩阵。

性能回归先复测和定位；不得直接提高阈值/关测试。需要校准目标时记录硬件、重复次数、噪声、正确性影响与用户体验依据，更新本文件并经审查；若改变 CPU-first 架构原则必须另写 ADR。超过预算项不能无说明发布为达标。
