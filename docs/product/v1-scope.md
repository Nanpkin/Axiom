# 产品范围：后台自动化小工具

## 成功是什么

用户用少量步骤表达“当某个条件发生/成立，执行明确任务”，保存后无需盯着界面；后台可靠工作、结果能解释、随时能暂停。新增一种条件或动作不必重写产品，日常空闲尽量不消耗 CPU。当前事实与交付顺序只在 [当前状态](current-state.md) 维护。

## 面向用户的模型

| 概念 | 用户理解 | 开发边界 |
|---|---|---|
| 自动化规则 | 何时执行、执行什么、何时停止 | 稳定 ID/版本、名称、条件、动作参数、启用状态 |
| 条件 | 例如指定程序运行时 | 真实观察来源；未知不是不满足；组合按实际场景开放 |
| 动作/任务 | 做一次，或在条件有效时保持设置 | Command 与 Desired State 独立，不把所有动作都当开关 |
| 执行策略 | 冲突怎么处理、结束后怎么办 | 默认值可解释；只有接通才提供选项 |
| 结果 | 做了什么、为什么没做、接下来怎么办 | 已保存、已启用、执行中、成功/失败是不同事实 |

“任务系统好”须体现为可控执行和可理解的失败处理：每个资源避免重复并发，取消/超时不假报成功，重启不重放危险命令，冲突有说明。多动作、顺序/失败策略、条件 AND/OR、时间触发等在真实需求出现时逐项交付，不以通用 DAG 编辑器或空任务队列充数。底层已有语义按需复用，不提前把所有参数暴露给用户。

## 交付准则

每个功能必须有一条真实路径：配置并保存 → 检测 → 执行 → 查看结果/原因 → 暂停 → UI 退出后继续。只完成地基、状态显示或文字草稿不算新增自动化能力。

HDR 是第一个验收场景；第二个不同场景检验扩展成本。新增能力必须有明确用户任务、适用通知源和真实动作，不按 Process/Time/Session/Service 等名称逐个铺空实现。候选不是承诺，不设置面向用户的“待接入能力”页面。

用户于 2026-09-28 明确要求的通用任务编辑架构已实施，不再使用 HDR 专用表单作为产品主编辑器。检测与动作独立注册，后台提供参数描述和兼容组合，UI 按描述生成配置界面；引擎通过独立编译接口接收配置。2026-10-04 接入第二组真实能力：程序运行/全部退出 → 启动/关闭程序，以及显式注册的内置插件模块和通用命令任务存储。具体能力和验证进度只看当前状态，不从本文推断全部扩展已经实现。

已复现的误执行、权限越界、丢数据、卡死、泄漏必须处理。无关极端情况记录后续，不重复扩展复审。文档、测试、抽象的投入均须能解释对本轮用户行为的作用。

## 早期开发重心

2026-10-09 所有者明确：优先扩充能改善 Windows 日常体验的实用检测与执行能力，开发者主动发现痛点、提出场景并逐项交付，不只等待用户提供想法，也不只整理框架。以真实场景和组合收益排序，具体候选见 [云端工作流](../development/cloud-workflow.md)。不提前承诺所有系统接口都能可靠支持。

## 产品约束与非目标

Windows 11 x64、本地优先，确定性规则，UI 可完全退出。CPU-first 在正常模式同样成立，通知按需共享、无工作等待、仅调度必要期限；性能策略与数值验收见 [性能政策](../development/performance.md)。不承诺绝对零 CPU。

V1 不做云账号依赖、远程/Web、任意脚本执行、AI 运行时判断、插件市场、跨平台、可视化编程语言、所有 Windows 能力覆盖。保留能力扩展边界，不把这些未来功能当当前前置。

## 发布验收

- 用户无需开发脚本完成安装、配置、暂停、查看结果和退出；真实任务及必要失败分支实测通过。
- 规则在正常/轻量模式按声明运行；冲突、未知、手动接管可解释；保留规则不被偷偷停止。
- UI 全退仍工作，安装/卸载/重启恢复与权限边界验证；不安全命令不补发，失败不高频重试。
- 全后台性能实测并校准，提供原始证据；未完成项明确显示在交付说明，不能借核心测试或短基线宣称产品完成。
