## 保留的后续想法与已知 API 障碍

- 有限有序动作仍有价值：一次打开计划文档、启动工具、整理窗口；之后围绕具体场景做最小逐项结果、失败策略和取消。当前不把工作流大框架或任意 AND 条件当作交付前置。
- 完整工作布局恢复仍是后续候选：用户显式保存窗口布局，处理缺屏、混合 DPI、多个同应用窗口及手动调整。先交付上表的指定屏幕动作，不把完整恢复系统当成必须先做的基础设施。
- 默认播放/录音设备切换：检测默认设备变化已有公开通知，切换系统默认设备缺少相应稳定公开 Core Audio 设置接口；未经专项 API 与权限核实，不依赖未公开 `PolicyConfig` 冒充可靠通用能力。
- 文件自动归档：已有文件名新建/重命名通知不证明写入/下载完成。若做复制/移动，要先选具体受支持流程，说明重名、占用、取消和数据保留；不存在通用“文件已下载完成”事件，不能默默轮询所有目录。
- 用户空闲/持续无操作：通用 `GetLastInputInfo` 只提供查询，并无可靠的任意空闲阈值系统通知。没有合规低成本设计及取舍证据时不提升为下一项，更不能开启键盘 hook 或采集输入正文。

## 当前媒体动作增量（独立分支）

用户新增能完成：锁屏或进入工作/游戏程序后请求暂停Windows当前媒体，也可用快捷键或定时请求播放、上一项、下一项。`media.current-control`和默认暂停的“锁屏后暂停Windows当前媒体”模板已接真实声明/编译/Agent/GSMTC适配；不更改现有指定应用音量。操作接受、已暂停无需操作、不支持/无会话/会话切换/权限失败分别解释；UI退出仍按规则工作，暂停不恢复播放。

精确指定exe媒体控制先被排除：GSMTC的AUMID没有可靠PID/完整路径映射。采用明确的“Windows当前媒体会话”目标，只调用 `GetCurrentSession`，不把任意枚举第一项当目标，不读取媒体标题、曲目或正文。公开WinRT类型和运行库已由现有Windows目标框架提供；Linux编译不证明权限。真实无包身份API的Windows只读CI、锁屏/播放器/浏览器实机效果均须独立验证；取消或超时可能已发送，不重试，不承诺返回后播放器已完成变化。
