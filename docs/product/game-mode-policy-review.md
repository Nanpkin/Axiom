# 游戏模式策略审阅

更新：2026-10-23。按审阅时实际注册的77项能力（36检测、41动作）、4个工具箱项目及主动使用观察审阅。以下是候选建议，不是自动套用到规则的策略；成本等级来自代码路径判断，未做新的CPU/GPU测量，不能当性能排名。私人任务逐项结论仅保留本机。

所有者后续明确：现有两条定时亮度任务不受游戏模式影响，保留原有行为。游戏模式作为状态检测提供，规则作者用AND/OR/NOT显式决定何时执行；不按本清单自动改写任何规则。组合判断和停采策略是不同层，逻辑不成立不代表其他检测已停止采集。

## 决策原则

游戏模式分别解决两件事，可同时命中：A减少持续采集、事件处理、查询及后台工作；B避免自动化改变画面、声音、焦点、网络或输入而打断游戏。低成本检测也可能触发强干扰动作；停止动作不一定省掉检测成本。

以整条规则的用途作最终决定，不按能力ID一刀切。游戏所需的HDR、语音热键、唤醒、游戏工具启动、必要Hosts解析可保留；工作/舒适度自动化通常暂停。手动暂停保持，显式手动操作与后台自动动作分别判断。游戏模式自己的进程检测、退出通知、必要恢复和停止保护必须继续。

优先暂停画面驱动的自动调亮度，暂不提供游戏中低频采样作为默认方案：它仍可能在游戏白场、菜单、爆炸等场景误触发，降频不能解决画面体验问题。对已有必要采样才讨论降频；事件驱动检测继续通知或按规则释放订阅，不改成定时查询。

## 检测逐项覆盖

“继续”只指来源没有充分理由默认停；若对应整条规则游戏期间暂停，应释放该规则的检测租约。共享来源仍有消费者时保留，不能承诺共享来源完全退出。

| 能力ID | 成本/触发特征 | 游戏模式建议 |
|---|---|---|
| `screen.content-bright` | A重点：DXGI采集、GPU归约、回读与CPU评分；area/regions均有活动画面开销，当前上限4Hz | 舒适度规则默认整条暂停，停止该消费者采集；同时属于B，避免自动调光 |
| `process.running`、`process.exited` | 初始目标快照、共享进程启动事件及精确退出等待；并非定时全进程扫描 | 继续游戏模式/HDR/必要工具用途；非必要规则可释放，不做“降低进程扫描频率” |
| `process.foreground` | 前台变化通知及身份查询；切窗/覆盖层变化时可能较多 | 游戏必要用途继续；非必要工作规则暂停，候选A事件处理成本 |
| `window.visible`、`window.absent` | 共享窗口事件、目标匹配；游戏启动器/窗口频繁变化可能放大查询 | 非必要规则暂停；保留明确游戏辅助用途，不笼统称高CPU |
| `window.state-is` | 窗口事件后重新判断最小化/最大化/普通 | 同上；游戏窗口布局动作还需B限制 |
| `window.foreground-covers-screen` | 前台、窗口、显示事件合并后读边框/显示器；全屏切换和覆盖层可触发 | 非必要时暂停；不将“覆盖屏幕”等同识别到游戏 |
| `audio.application-active` | 音频会话通知、会话/进程身份读取；新会话较多时有工作量 | 非必要统计/联动可暂停；语音/游戏必要用途继续，属于A候选而非高频采样 |
| `media.playback-state` | 当前媒体会话通知，变更后读取 | 来源通常继续；自动暂停媒体/改音量的规则按B处理 |
| `audio.default` | 默认音频设备通知 | 继续，不为降频丢设备切换事件 |
| `audio.mute-state` | 默认端点静音通知 | 继续，保留语音和隐私用途；不推断实际收音 |
| `file.arrived` | 本地目录事件；大量下载/解压时可有密集事件 | 与游戏无关的文件处理规则暂停；不补放期间积累的事件，不改成慢速目录扫描 |
| `interval.elapsed`、`time.windowed-interval` | 必要deadline定期触发；频繁工作主要取决于间隔与动作 | 非必要周期工作暂停；不偷偷改用户间隔，退出不补排队动作 |
| `time.daily`、`time.monthly`、`time.once` | 最近日历deadline与时钟通知，空闲成本低 | 通知源继续，按动作与任务用途决定到期跳过；不能假记成功 |
| `time.window-once` | 时段边界deadline、持久去重及有界重试 | 游戏期间可跳过非必要动作，不把跳过标成成功；恢复不因模式退出重放 |
| `axiom.started` | 一次后台启动事件 | 必要游戏/基础工具继续；工作应用启动和自动整理按B审阅 |
| `keyboard.hotkey` | 系统热键注册，按键时响应 | 用户主动的音量、麦克风等继续；与游戏键冲突的单条禁用，不能全停控制入口 |
| `display.count`、`display.hdr-state` | 显示变化/HDR通知及按需读取 | 继续游戏所需检测；避免游戏中由显示变化触发整理/切换 |
| `screen.state` | 会话屏幕电源通知 | 继续；自动关屏/静音规则单独审阅 |
| `session.lock-state`、`session.user-presence` | Windows会话/在场通知 | 继续；不能把玩游戏无键鼠变化当作离开，也不能一并停隐私规则 |
| `power.state`、`power.saver-state`、`power.scheme-state` | 电源/电量阈值/方案通知 | 继续电池与电源信息；性能或亮度动作按B判断，不隐藏低电量状态 |
| `network.category-state`、`network.internet-state` | Windows网络状态通知，不主动ping/HTTP | 继续；按需释放非必要规则，不增加慢速网络探测 |
| `wifi.profile-connected`、`wifi.profile-disconnected` | WLAN通知与当前配置读取 | 继续；离网锁屏等隐私用途不能自动归为可丢任务 |
| `usb.device-present`、`usb.device-absent` | 指定实例设备通知及快照 | 继续，保留耳机/外设用途；不轮询USB |
| `system.event` | 显示、会话、设备等系统环境事件 | 继续必要事件；游戏期间跳过非必要响应动作，不停全局恢复消息 |

## 执行动作逐项覆盖

动作通常按请求执行，没有“空闲动作采样频率”。A应审查触发频率、并发、进程启动/解析等真实工作；B应在执行前拦住非必要自动动作。下表的暂停建议默认针对后台自动化，不自动禁止用户专门按热键发起的音量、麦克风等操作。

| 能力ID | 对游戏的影响 | 建议 |
|---|---|---|
| `display.brightness`、`display.brightness-adjust`、`display.brightness.restore` | B重点：画面突然变暗/变亮；渐变期间还有多次写入 | 舒适度/定时自动调光默认暂停；用户手动调光可保留 |
| `display.hardware-brightness`、`display.hardware-brightness-adjust`、`display.hardware-brightness.restore` | 同上，另有硬件读写和渐变工作 | 规则作者自行决定；现有两条定时亮度明确继续执行、不受游戏模式影响。选择条件恢复型暂停时按原保护收尾，不能强写100% |
| `display.hdr` | 切换会影响显示体验；也可能正是游戏所需设置 | 游戏专用HDR保留，非游戏自动切换可暂停。旧兼容后端不支持通用外层门禁，不能直接套暂停而忽略其退出恢复语义 |
| `display.off-request` | 直接打断画面 | 非必要自动关屏暂停；用户明确关屏仍属独立请求 |
| `window.state`、`window.state.restore`、`window.monitor` | 最小化、置顶、调整大小或移屏可能打断游戏/覆盖层 | 非必要自动整理暂停；恢复本身也可能移动窗口，须沿原身份/placement保护 |
| `window.foreground-layout`、`window.foreground-monitor` | 操作执行时的前台，容易命中游戏 | 默认不执行非必要自动请求；仅明确手动入口可例外 |
| `window.close`、`program.close` | 可能关闭游戏、启动器、语音或外设工具 | 非必要自动关闭暂停；不要把游戏依赖当后台垃圾清理，更不增加强杀 |
| `program.start` | 启动成本、可能弹窗抢焦点 | 游戏依赖工具保留；办公/下载/扫描等非必要自动启动暂停；已发出启动不强制撤销 |
| `target.open`、`open-target.batch`、`work.prepare` | 打开浏览器/文件/一组应用，抢焦点和短时资源竞争 | 工作自动化默认暂停；停止尚未开始步骤，已开始项不关闭回滚 |
| `keyboard.send` | 模拟按键可能落入游戏，误操作 | 自动发送默认暂停；不要为恢复/验收模拟游戏按键 |
| `audio.playback`、`audio.playback-adjust`、`audio.playback-toggle`、`audio.playback.restore` | 游戏声音变化、静音；恢复也可能发声 | 非必要自动调整暂停；用户手动音量/静音继续；恢复按当前值与基线保护 |
| `audio.application` | 可改变游戏或语音程序音量，也可用于降低其他应用声音 | 按实际目标判定；保留用户明确的游戏混音规则，暂停无关自动调整 |
| `audio.microphone`、`audio.microphone-toggle`、`audio.microphone.restore` | 影响队伍语音和隐私；恢复取消静音可能收音 | 保留用户主动语音控制/隐私用途；非必要自动切换暂停，不能统一自动解除静音 |
| `media.current-control` | 暂停/播放/切曲可能影响背景音乐，当前会话未必是预期应用 | 自动控制可暂停；用户主动媒体热键继续，不因游戏结束自动播放 |
| `notification.show`、`notification.sound` | 提醒覆盖画面或打断听音 | 非关键自动提醒/声音暂停；明确重要的日历/电池/安全提醒由用户选保留，不积压退出后一口气播放 |
| `power.scheme`、`power.scheme.restore` | 可影响功耗、温度与帧率，既可能有益也可能降低性能 | 游戏性能方案可保留；办公节能联动可暂停；不代用户强制高性能，避免退出/恢复反复切换 |
| `program.priority`、`program.priority.restore` | 改变调度；调低游戏/语音或调高其他工作可能不利 | 仅明确游戏优化规则保留；其他自动优先级调整暂停，不把它说成CPU限额 |
| `power.keepAwake` | 有助防止游戏期间睡眠；请求保持不需要不断写入 | 默认保留游戏唤醒用途，不能为了省后台停掉；游戏模式本身不额外强制屏幕常亮 |
| `hosts.update` | DNS/DoH解析、hosts写入是A候选工作；解析结果变化也可能影响游戏连接/重连 | 不按网络一刀切。必要游戏解析保留；周期刷新可选择游戏时跳过，进入模式不还原现有hosts。是否跳过须按任务用途确认 |
| `session.lock` | 锁屏会中断游戏，但也可能是安全/隐私要求 | 普通离开/休息提醒型可选择暂停；离网等保护规则默认保持原行为，须逐条由用户决定例外 |
| `taskbar.auto-hide`、`taskbar.auto-hide.restore` | 桌面/窗口布局可能变化；也可能改善无边框游戏体验 | 游戏用途保留，其他自动切换可暂停；不为进入模式反复恢复/应用 |
| `tray.hide` | 通常不改变游戏画面，执行时有Shell查找/写入工作 | 保留原启动整理；无需求不反复执行，无需默认暂停 |

## 工具箱与附加后台行为

| 项目 | A资源策略 | B体验策略 |
|---|---|---|
| Steam游戏整理 | 启动扫描Steam元数据可能有磁盘工作，可将非必要自动扫描延后；不新增定时扫描 | 保留已有进程组，不能清空用于游戏模式的名单；用户“立即检查”仍可显式操作 |
| 托盘管理 | 仅启动模式完成后没有理由反复跑；持续模式由Shell/进程事件驱动，可仅在证据表明事件噪声大时暂停非必要重扫 | 当前默认保留，避免游戏模式切换令图标反复出现/消失；退出不重复整个启动批次 |
| 快捷键+滚轮亮度 | 不是画面采集；若用户选择游戏时停用，应释放对应输入hook/租约，不停全部输入能力 | 当前默认建议游戏时停用这个工具，避免游戏中的组合键+滚轮误调亮度；用户明确需要时可保留，不等同禁用所有手动音量/语音热键 |
| 定时Hosts | 同`hosts.update`；已保存网络设置保留，非必要刷新可跳过 | 必要游戏解析例外保留，暂停不撤销已有hosts/代理配置，不据此承诺网络不断开 |
| 主动使用观察 | 前台/进程/窗口/音频元数据记录和存储可在事件密集时增加工作；默认建议暂停非必要观察并记录空档 | 若用户正在专门观察游戏，则让用户明确继续；暂停期间不伪造行为，恢复不回填。建议生成/导出按需触发，不增加后台AI |
| 活动记录、UI、恢复与控制 | 保留必要状态/失败/恢复记录，UI继续按需刷新；不以关闭日志假称解决采集成本 | 游戏模式不隐藏错误，不停IPC、手动关闭/退出或恢复通道 |

## 进入和退出的实现边界

1. 只按已明确策略处理规则；进入后先取消未发出的非必要延迟、排队与重试，释放相应检测。已经发出的Command可能已生效，不回滚、重放或假称未发生。
2. Desired State暂停沿现有仲裁和严格恢复：只在身份与最后写入值仍能确认时恢复最初基线；外部接管/Unknown让出。只有条件恢复型亮度动作（`.restore`）具有这个租约恢复语义；已经完成的一次性调光不会因开启游戏模式自动变亮。亮度渐变中断用已有修复逻辑，不能留下降亮值再把它当新基线。HDR游戏规则不属于默认暂停对象。
3. 恢复工作不能粗暴冻结，否则可能把当前降亮/静音/布局遗留在游戏中；同样不能强行恢复覆盖用户改变。UI明确显示暂停原因与恢复未确认。
4. 退出仅恢复允许的检测，重新读取真实当前状态。状态型Desired State按新快照评估，Command不因游戏结束补发历史事件。明确日期提醒或失败重试的跳过状态须可解释，不记动作成功。
5. 游戏模式不是全局暂停：手动暂停、HDR/时段门禁、游戏模式各自独立；退出不重新启用用户手动停掉的任务。进程事件订阅应共享，模式自动检测绝不能跟随被暂停的普通规则一起停掉。
6. 当前接入顺序为真实模式状态与可组合状态检测；画面亮度规则是否加入限制由用户配置，两条现有定时亮度不受影响。采集暂停/降频与可选滚轮工具策略需后续单独接入。本文不授权自动改写现有规则。
