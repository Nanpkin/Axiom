# 游戏模式

更新：2026-10-23。游戏模式是由后台管理、可供自动化读取的会话状态，不是全局暂停开关。现有任务不自动加入限制；所有者明确两条现有定时亮度任务不受影响。

## 使用方式

设置首页→游戏模式，分别选择手动开启和指定程序自动开启。进程输入复用检测能力的多选控件，支持exe名称、程序文件、批量输入和进程组；大小写不敏感去重，最多128项。选入后独立保存，组变化不暗改名单。

有效状态 = 手动开启 OR（自动开启已启用 AND 任一所选程序运行）。关闭手动开关只释放手动请求，仍按自动检测决定；全部目标退出且没有手动请求才结束。自动状态无法确认时保持未知，除非手动开启已经能确定有效状态为真。关闭UI不影响后台观察。

新建规则时可选择“游戏模式”状态检测，使用通用“全部满足 / 任一满足 / 不满足此条件”（AND/OR/NOT）组合。例如：

- 全部满足：画面明亮条件；不满足此条件：游戏模式已开启。
- 全部满足：指定程序正在运行；游戏模式已开启。

每个叶子仍必须支持同一动作；原不支持组合的旧HDR适配器不会因此开放组合。模式本身不决定亮度、声音或网络设置，规则作者自行决定动作与条件。游戏状态未知时NOT仍是未知，不冒充关闭。首次读取、重新连接或新建规则不补发一次性命令；持续动作仍按已知初始条件和原恢复contract评估。

## 保存与状态

UI只向Host读取和保存配置；版本冲突和未确认不假报成功，保留输入，可显式重读。设置页显示“读取时”的真实状态与原因，按需刷新，无状态轮询。未保存输入在本窗口切页、返回和刷新中保留，关闭窗口先确认。

旧game-mode-preset.json仅为早期UI预设：显式“导入原预设”填入表单，仍须保存才能生效；不会静默激活，也不删除。宿主配置原地保存，重启重新读取自动进程状态，观察缓存不当持久事实。

## 条件逻辑与资源策略的区别

AND/NOT使规则条件不成立，会按动作原语义取消尚未发出的请求或释放Desired State；不自动停止其他叶子检测的采集。比如NOT游戏模式能防止游戏中自动调光，但不代表DXGI采集已经停止、资源占用已下降。没有测量不宣称性能收益。

后续若要真正暂停/降频某个监测，须显式接入采集生命周期，复用共享订阅、取消、Unknown和手动接管保护。共享来源还有消费者时保留；游戏模式自动进程观察不能随普通规则暂停，否则无法可靠退出。事件驱动能力不改成轮询。

候选审阅见[策略矩阵](game-mode-policy-review.md)，它不授权自动改写用户任务。两条定时亮度继续原有调度；画面亮度等规则是否加入游戏模式限制由用户选择。

## 动作与恢复边界

已经发出的Command可能生效，暂停不回滚、不重放。一次性调光不会因游戏模式开启自动变亮；只有条件恢复型动作沿原租约，在身份和最后写值确认、无外部接管时恢复最初基线。Unknown或恢复不明不能强行覆盖。手动暂停、HDR/时段门禁与游戏模式条件各自独立。

当前实现与验收证据以[当前交接](current-state.md)为准；本页不代表所有监测已接入停采策略。
