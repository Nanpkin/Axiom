# CPU-first 性能模型

性能是设计输入，不是 UI 完成后的优化。减少 CPU 时间、唤醒与持续后台工作优先于压低内存数字；正确性、权限和用户承诺不可用性能换取。

开发阶段以选择合适检测方式和审查工作策略为常规，不要求每轮数值测量；异常诊断与发布验收的测量时机统一见 [性能政策](../development/performance.md)。不把用户电脑同时运行 AI 开发和其他工作的混合负载读数作为严谨性能结论。

## 事件到工作的预算路径

1. 优先评估适用的 ETW、WTS、Power Notification、Windows 事件/通知 API。先选最窄、成本最低且权限适用的通知源；“使用 ETW”并不自动低成本，禁止无需求打开全系统高频 trace。
2. Provider 回调轻量投递；StateStore 去重；依赖索引只唤醒受影响规则。禁止固定频率扫描进程、显示、服务或全部规则。
3. 昂贵观察器按有效依赖引用计数激活；没有订阅便停。UI 退出释放 UI-only 需求；用户保留规则的依赖不得停。
4. 调度器维护 pending deadline 集合，逻辑上只等待最近一次唤醒；没有任务就无限等待事件，不用短周期 tick 检查队列。deadline 到达只处理已到期工作。
5. 写日志批量、有界、非关键可丢弃并计数；空缓冲不 flush。失败使用 capped exponential backoff，重试上限后等待外部变化/用户动作；成功或新 generation 重置对应状态，不重启所有定时器。

退避公式基于 attempt 的指数增长和 cap；生产若需 jitter，通过可注入、可记录的来源提供，并作为调度输入测试，不让纯规则决策依赖隐藏随机性。

## 事件风暴与背压

每个入口有界队列、消费者背压和丢失指标。latest-value 观察只在不影响规则语义时按 key 合并；需要命令触发边沿、minimum duration 或准确转移的观察不能无条件合并。发现 gap 时把相关判断置 Unknown，取消连续时长认定，快照对账后重新建立状态；不能把可能丢失的命令边沿补成“已执行”。支持来源提供序列号或明确 gap 信号；无法证明无丢失时保守处理。

关键控制（接管、权限、模式、取消）需要保留处理容量，不能饿死在普通事件队列后。相同资源单在途并限制全局并发；不能以 unbounded Task.Run 消化压力。

## 轮询例外协议

仅在相关能力无可用通知或通知无法满足正确性时提出例外；记录 API 调研证据、最大容忍延迟、正常/轻量间隔、按需启停、退避/停止条件、成本预期和后续测量安排。经 ADR 明确后才可实现；开发期不强制先取得实际 CPU/唤醒数值，发布前需验证实际成本。不能以“先跑通”为由引入无依据轮询。有效调度（用户指定时间、退避、超时、到期）不是无理由轮询，但也必须能解释每次唤醒。

详细数字只在 [performance.md](../development/performance.md) 维护；模式行为只在 [lightweight-mode](lightweight-mode.md) 维护。性能测试必须覆盖真实 Service/Agent 总开销；早期 Engine harness 不能冒充完整产品结果。
